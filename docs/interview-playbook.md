# 面试讲解手册

> 所有业务背景、数据、产品和客户均为虚构。讲解时应主动说明这是可公开复现的作品集项目，而不是伪装成真实客户项目。

## 1. 30 秒版本

“我做了一个商业分析 AI Agent。用户可以用自然语言问销售、库存和制度问题；系统会判断该查结构化数据还是知识库，调用受控工具，再返回带来源和执行轨迹的答案。它默认有不依赖 API Key 的本地模式，方便复现，也支持接模型增强复杂表达理解。我还配了 API、自动化测试和离线评测，重点不是聊天页面，而是可核验、可观测和可降级的 Agent 工程闭环。”

## 2. 两分钟版本

“项目背景是业务人员通常需要在报表和制度文档之间反复切换，普通大模型虽然回答快，但数值容易算错、结论也很难追溯。所以我把系统设计成一个 evidence-grounded Agent。

请求进来后，Agent 先做意图路由和实体抽取。销量、趋势、库存等问题走确定性 Python 工具；规则和口径问题走轻量 RAG；复合问题会合并两类证据。最后统一返回 answer、tools、sources、confidence 和 trace。前端把结论放在最上面，来源和工具轨迹可展开。trace 展示的是可审计操作，不是模型思维链。

工程上我保留了 Local 和 OpenAI 两种模式。Local 模式是可重复的基线，没密钥也能端到端演示；OpenAI 模式提升复杂语言理解，但核心指标仍由工具计算。评测不做逐字匹配，而是检查路由、工具、参数、事实、引用和拒答，还把安全案例设为硬门槛。

这个项目让我真正处理了 Agent 的几个关键问题：RAG 和工具调用怎么分工，如何防止模型编数，如何做可观察 trace，以及怎样让 demo 可复现、方便面试官验证。”

## 3. 五分钟 Demo 脚本

### 第 1 分钟：建立问题

打开界面，指出模式标识和“数据全部虚构”的声明。说明目标是把分散在表格和文档中的经营信息变成可追溯答案。

### 第 2 分钟：结构化问题

选择销售概览或区域对比问题。先看回答中的数字和 KPI，再展开来源，说明数字来自工具计算而非模型心算；展开 trace，展示路由和工具步骤。

### 第 3 分钟：知识问题

询问一个授权规则或指标口径。展示命中的文档片段和引用，解释为何这类问题走 RAG 而不是结构化聚合。

### 第 4 分钟：边界问题

输入一个数据集中不存在的产品/日期，或要求给出没有证据的确定原因。理想行为是提示缺少数据或要求澄清，而不是编造答案。

### 第 5 分钟：工程闭环

快速展示 API schema、测试和评测报告，说明 Local 模式如何保证他人无需密钥即可复现。最后补充生产化差距：真实权限、脱敏、监控、审批和数据治理仍需建设。

## 4. STAR 讲法

### Situation

业务问答同时涉及结构化指标和非结构化规则。传统报表检索慢，直接让大模型回答又存在数值幻觉和不可追溯问题。

### Task

做一个可公开复现的 Agent 原型，既能展示端到端产品体验，也能用测试和评测证明结果质量，并明确数据与生产边界。

### Action

- 设计统一的 Agent 输出协议；
- 将确定性计算封装为白名单工具；
- 为制度文本实现轻量检索并保留 citation；
- 增加 Local/OpenAI 双模式与失败降级；
- 记录路由、工具、耗时和状态 trace；
- 用黄金集分别评测路由、参数、事实、引用和拒答；
- 提供 Streamlit、FastAPI、测试和容器化入口。

### Result

形成一个可在本地完整运行、每条关键结论可检查来源、每次工具执行可审计的作品集项目。这里不要编造用户数、营收提升或准确率；如需量化，应引用现场运行生成的真实评测结果。

## 5. 高频深挖问题

### Q：为什么要做 Local 模式？直接接大模型不是更像 Agent 吗？

Local 模式不是为了替代模型，而是提供确定性基线和可靠演示。它让 CI、单测和面试现场不受密钥、网络、配额影响。模型模式与它共享工具、来源和评测协议，所以可以清楚比较模型带来的增益与回归。

### Q：RAG 和工具调用怎么选？

需要精确过滤、聚合或排序的问题交给结构化工具；答案存在文档中的规则/口径问题交给 RAG；原因分析和建议往往两者结合。核心原则是让计算系统算数，让检索系统找已有事实，让模型负责理解和表达。

### Q：如何降低幻觉？

核心数字不让模型心算；回答必须基于 ToolResult 和检索片段；来源与答案一起返回；低相关、无数据和工具失败时降低置信度或明确拒答；最后用黄金集持续检查事实与引用。

### Q：为什么 trace 不展示完整思维链？

业务审计真正需要的是路由、工具、参数摘要、来源、状态和耗时。完整思维链既不稳定，也可能包含敏感信息。系统提供可验证的操作证据，而不是暴露模型私有推理。

### Q：多轮对话怎么处理？

通过 session id 隔离会话，只保留完成指代解析所需的最小上下文。工具参数每轮仍要重新验证，不能因为上一轮提过某区域就跳过权限和口径检查。生产环境还要增加会话过期和删除机制。

### Q：如何评价引用真的正确？

不是检查“有没有 sources 字段”，而是把关键事实映射到黄金 source id，并人工抽样判断片段是否支持结论。引用正确率和覆盖率需要分开：错误引用很多与缺少引用是两种问题。

### Q：如果数据和文档冲突怎么办？

不应由模型擅自选一个。输出应并列展示冲突、各自时间和来源，提示可能的口径或版本差异，并交由有权限的人确认。trace 记录使用了哪些版本。

### Q：怎么上生产？

先把本地文件替换为只读数仓和受控文档源，再补齐身份传递、行列级权限、租户隔离、脱敏、密钥管理、监控告警、评测门禁与数据生命周期。任何写回都需要预览、人工审批、幂等和审计。

### Q：这个项目最难的技术点是什么？

可以回答：“难点不是调一个模型 API，而是定义不同能力之间的协议和失败边界。工具、RAG、UI、API 和评测必须使用同一个结构化结果，否则很快会出现演示能跑但无法验证、也无法维护的问题。”

### Q：你会如何继续优化？

优先从失败案例驱动：先看 trace 判断是路由、参数、检索还是生成问题，再针对性优化。其次增加混合检索、引用对齐和多轮指代。最后才是更换模型；换更大模型不是所有问题的默认答案。

## 6. 可用于简历的表达

下面的表述不包含虚构业务收益，可按实际评测结果补充量化数字：

- 独立设计并实现面向商业分析的 AI Agent，编排结构化数据工具与知识库检索，输出带 citation、confidence 与 execution trace 的可核验答案。
- 构建 Local/OpenAI 双运行模式，以确定性本地链路支持无密钥复现、CI 回归和故障降级，并通过统一协议复用工具与评测体系。
- 建立覆盖路由、工具参数、事实、引用、拒答与安全对抗的离线黄金集和自动化评测流程，支持逐案例错误定位。
- 完成交互式 Streamlit 界面、FastAPI 服务、测试与容器化交付，明确演示数据、隐私与生产化边界。

只有当仓库确实实现且能现场证明时才使用对应表述。不要写“准确率提升 30%”“节省 80% 人力”等无法复算的数字。

## 7. 讲解中的避坑

- 不说“训练了一个大模型”，除非确实做了训练或微调；本项目主要是 Agent 编排、RAG 和工具工程。
- 不把规则路由包装成自主规划，也不把模板回答说成模型生成。
- 不声称使用真实医药数据；主动强调合成数据是为了公开展示与隐私安全。
- 不只演示成功案例；展示一次无数据/拒答能更好体现工程成熟度。
- 不背诵框架名。围绕问题、取舍、证据、失败和迭代讲，面试官更容易判断真实参与度。
