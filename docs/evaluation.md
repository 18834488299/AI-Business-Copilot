# 评测方法

> 评测集及其公司、产品、区域和数值全部为虚构。报告中的结果只描述当前演示版本，不外推到真实生产环境。

## 1. 评测目标

这个项目不把“回答看起来不错”当成完成标准。评测需要分别回答：

1. 路由是否选对了能力？
2. 工具是否用了正确参数？
3. 数值和事实是否正确？
4. 引用是否真的支持结论？
5. 不该回答时是否会拒绝、澄清或降级？
6. 整个过程的延迟、稳定性和成本是否可接受？

本地模式承担可重复的回归基线；模型模式在同一案例集上运行，用于比较自然语言理解能力，而不是使用另一套更宽松的标准。

## 2. 黄金集设计

一条评测案例至少包含以下字段：

```json
{
  "id": "sales_region_decline_001",
  "category": "structured_analysis",
  "question": "本周哪个区域下降最多？",
  "expected_route": "sales_analysis",
  "expected_tools": ["regional_sales"],
  "expected_facts": {
    "region": "虚构区域",
    "direction": "down"
  },
  "required_source_ids": ["sales_demo"],
  "forbidden_claims": ["未经数据支持的原因"],
  "tags": ["time_range", "ranking"]
}
```

黄金集不要求逐字匹配答案。它约束可客观检查的路由、工具、事实、来源与安全行为，让语言表达可以变化。

## 3. 案例覆盖矩阵

| 类别 | 应覆盖的问题 | 主要检查项 |
|---|---|---|
| 结构化分析 | 汇总、对比、排序、趋势 | 数值、过滤条件、单位、工具 |
| 知识检索 | 规则、口径、流程 | 文档命中、引用、低相关降级 |
| 复合推理 | “发生了什么 + 为什么 + 怎么做” | 多工具编排、事实/推断分离 |
| 多轮对话 | 指代、省略、连续追问 | session 隔离、上下文继承 |
| 边界输入 | 空问题、未知产品、无数据日期 | 澄清、无数据提示、不编造 |
| 安全对抗 | Prompt injection、索要密钥、越权指令 | 工具白名单、敏感信息保护 |
| 鲁棒性 | 同义改写、错别字、中英混输 | 意图稳定性、参数抽取 |

每个工具至少需要正常、边界、空结果和错误四类案例。新增工具时，评测集和单元测试必须同步增加。

## 4. 核心指标

### 4.1 Route Accuracy

`正确路由案例数 / 总路由案例数`

适合发现“知识问题误走结构化分析”或“复合问题只调用一个能力”。对允许多条合理路径的问题，可将期望路由定义为集合。

### 4.2 Tool Precision / Recall

- Precision：实际调用的工具中，有多少是必要的。
- Recall：案例要求的工具中，有多少被调用。

这能同时惩罚漏调用和无意义的过度调用。生产系统中，过度调用会增加延迟、成本与风险。

### 4.3 参数准确率

对区域、产品、时间范围、Top-K 等参数逐字段比较。数值可设置容差；日期应先归一化。只检查“调用了正确工具”不够，错误参数同样会得到错误结论。

### 4.4 Fact Accuracy

把回答中的关键事实和工具结果或人工标注事实比较：

- 精确数值：绝对/相对误差；
- 类别和方向：exact match；
- 排序：Top-K overlap 或 Kendall 相关；
- 文本事实：人工或规则判定是否被证据支持。

不要用另一个模型的单一分数替代所有事实检查。

### 4.5 Citation Correctness / Coverage

- **正确率**：返回的来源是否实际支持对应结论。
- **覆盖率**：需要证据的关键结论中，有多少带有效来源。

仅仅“返回了一个来源数组”不代表引用正确。最好在黄金集中标记每个关键事实对应的 source id。

### 4.6 Abstention Accuracy

当数据缺失、问题越界或证据不足时，Agent 是否正确拒绝确定性回答并指出缺口。这是商业系统中与准确率同等重要的指标。

### 4.7 性能与稳定性

- P50 / P95 端到端延迟；
- 各工具 P95 延迟；
- 异常率和超时率；
- 单请求模型 token / 成本（仅模型模式）；
- 相同输入的结构化事实一致性。

## 5. 评分方式

建议同时保留分项结果与总分，避免一个高总分掩盖严重安全问题。示例权重：

| 维度 | 权重 |
|---|---:|
| 事实准确 | 30% |
| 路由与工具 | 20% |
| 参数正确 | 15% |
| 引用正确与覆盖 | 20% |
| 拒答/边界 | 10% |
| 格式完整 | 5% |

安全案例使用硬门槛：一旦出现密钥泄露、越权工具执行或真实敏感数据输出，不能靠其他分项抵消。

## 6. 自动化与人工评测分工

### 自动化适合

- 路由、工具名、参数和 source id exact match；
- 数值容差与排名比较；
- 输出 schema、trace 完整性；
- 延迟、错误率和回归差异；
- 典型注入字符串和敏感字段扫描。

### 人工适合

- 建议是否可执行；
- 事实、推断与建议是否清晰分离；
- 引用是否真正支持自然语言结论；
- 语气是否适合业务用户；
- 信息不足时的澄清是否有效。

如果使用 LLM-as-a-judge，应抽样人工复核、固定 rubric、保存 judge 模型版本，并避免让同一模型既生成又无监督地给自己打分。

## 7. 回归流程

1. 固定演示数据版本与评测集版本。
2. 在 Local 模式运行全部案例，得到确定性基线。
3. 如配置密钥，在 OpenAI 模式运行同一集合。
4. 输出逐案例明细和汇总指标，不只输出总分。
5. 与主分支基线比较，标出新增失败与改善。
6. 对所有失败检查 trace，区分路由、工具、检索和表达问题。
7. 高风险回归未解决前不合并。

仓库提供的离线 runner 应能通过类似以下方式执行：

```bash
python -m evaluation.run
```

实际参数以命令帮助和仓库实现为准。评测输出应放在可忽略的结果目录，不把 API Key 或完整敏感提示写入报告。

## 8. 面试现场的评测演示

推荐选择三条问题：一条结构化分析、一条知识检索、一条无答案边界。展示同一返回协议中的答案、来源和 trace，再运行离线评测。这样能证明系统不仅有漂亮 UI，也有可重复的工程验收标准。

如果某个模型案例失败，应直接打开 trace 说明失败发生在哪一层，以及准备如何改进；这通常比回避失败更能体现工程判断。
